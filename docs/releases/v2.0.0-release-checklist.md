# HighTac Platform 2.0.0 Release Checklist

This checklist defines the evidence required for Git tag `v2.0.0`. The generated
release report is authoritative for artifact hashes and gate status; this file
does not contain placeholder hashes that could be mistaken for real artifacts.

## Release Identity

- Product version: `2.0.0`
- Expected immutable Git tag: `v2.0.0`
- Distribution target: `internal_lan`
- Windows upgrade baseline: `HighTacPlatform-1.0.0-x64.exe`
- Windows candidate: `HighTacPlatform-2.0.0-x64.exe`
- Android candidate: final non-debuggable, release-signed `2.0.0` APK

The release report must show a clean worktree and `v2.0.0` pointing at the
reported commit. Build output created before that condition is an internal
candidate only.

## Artifact Evidence

- [x] Generate the final APK SHA-256 from the exact distributed APK.
- [x] Generate the installer SHA-256 from the final signed or unsigned bytes.
- [x] Verify the installer `.sha256` sidecar against those exact final bytes.
- [x] For this `internal_lan` release, verify an unsigned installer is reported
      as `internal_lan_unsigned` with Authenticode status `NotSigned`.
- [ ] For any future `public_distribution` report, require Authenticode status
      `Valid`, the expected signer, and a timestamp certificate.
- [x] Run the release artifact secret scan against the final payload.
- [x] Generate both JSON and Markdown reports with `New-ReleaseReport.ps1`.

An installer built without a certificate is explicitly classified as
`internal_lan_unsigned`. That is an accepted, non-blocking state for this
private-LAN 2.0.0 release. It is never a public signed package. Selecting
`public_distribution` changes Authenticode into a mandatory release gate.

Record commands and exact results in `v2.0.0-evidence.json`, then regenerate the
release report. A required item must be `passed`; `pending` and `not_run` block
release readiness.

## Recovery And Credentials

- [x] Stop and restart only `HighTacMqttBroker`; verify the API distinguishes
      broker state from station state and recovers subscriptions.
- [x] Stop and restart only `HighTacPlatform`; verify Android reports API loss
      and resynchronizes without losing bindings.
- [x] Disconnect and rejoin Android Wi-Fi; verify cached reads remain clear and
      writes resume only after the API is reachable.
- [x] Power-cycle the real station; verify offline timeout, reconnect, and a
      subsequent acknowledged command.
- [x] Record the provider-credential verification disposition. For this
      `internal_lan` release, the user explicitly waived provider-console
      revocation verification. This is not a claim that the historical keys
      were revoked; replacement values remain only in the protected backend
      environment and final artifact scans contain no credential values.

## Windows Upgrade Rehearsals

Approved host:

- [x] Complete a successful 1.0.0 to 2.0.0 upgrade on an approved Windows host.
- [x] Record sanitized service health and data-preservation evidence.
- [x] Restart Windows and verify both HighTac services return as Automatic,
      API readiness passes, MQTT listens on 1884, and the station reconnects
      without manual service startup.
- [x] Treat historical failed host logs as diagnosis only; do not commit logs or
      ProgramData.

Windows Sandbox:

- [x] Fresh install the 1.0.0 baseline.
- [x] Exercise service start/stop/restart and broker control.
- [x] Upgrade to 2.0.0 and verify ProgramData/database preservation.
- [x] Exercise keep-data uninstall/reinstall.
- [x] Exercise explicit delete-data uninstall.
- [x] Preserve only the sanitized
      `HighTac-Sandbox-Rehearsal.json` result outside runtime data.

The historical host install and upgrade logs ended with deployment configuration
exit code 1 because the launcher reused PowerShell `$Matches` after a second
regular expression and decoded empty environment values. The launcher now
captures the encoded value before namespace validation. Installer static tests
include both an ordering assertion and an isolated parser behavior regression.

## Ownership Boundary

The release team owns every gate above, including one-phone/one-real-light-strip
2.0.0 smoke testing and both Windows upgrade rehearsal records.

Only the final field-scale acceptance with 10 real Android phones and 2000 real
light strips remains a user-owned field acceptance. It is intentionally recorded
as external and is not claimed as completed by Codex. Provider-console revocation
verification is separately recorded as an explicit user risk waiver for this
internal-LAN release, not as a completed verification.
